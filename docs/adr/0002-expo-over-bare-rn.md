# ADR-0002. Bare RN CLI 대신 Expo SDK 57 + CNG

- 상태: 채택
- 일자: 2026-08-11

## 맥락

기존 프로젝트는 `@react-native-community/cli` 기반 bare 워크플로이며 `ios/`, `android/` 폴더를 커밋하고 `Dockerfile`로 APK를 빌드했습니다.

재구축 기반을 정하면서 Expo를 검토했으나, **"Expo는 네이티브 기능이 제약된다"**는 우려가 있었습니다. 만들려는 것이 지도·위치 기반 앱 — 즉 네이티브 의존도가 높은 도메인이라 이 우려는 정당한 검토 대상입니다.

## 결정

**Expo SDK 57 + CNG(Continuous Native Generation)** 를 채택합니다. 네이티브 폴더는 커밋하지 않고, 네이티브 설정은 config plugin으로 선언합니다. 실기기 개발에는 `expo-dev-client`를 사용합니다.

## 근거

1. **우려의 근거는 실재했으나, 시점이 지났습니다.** ~2021년 이전 Expo는 managed workflow만 존재했고 커스텀 네이티브 코드를 쓰려면 `eject`로 Expo를 이탈해야 했습니다. **EAS Build + Config Plugins** 도입 이후 문제의 성격이 "네이티브 코드를 쓸 수 있는가"에서 "네이티브 폴더를 커밋하는가"로 바뀌었습니다. 커밋하지 않아도 네이티브 설정은 플러그인으로 주입됩니다.

2. **React Native 공식 문서가 Expo를 권장 시작 경로로 명시합니다.** 서드파티의 선호가 아니라 RN 팀 자체의 입장 변화입니다.

3. **지도·위치 도메인에 필요한 모듈이 1st-party로 존재합니다.** 특히 `expo-maps`가 SDK 버전과 동기화되어 배포된다는 점(57.0.1)은 지도가 Expo 코어 관심사에 들어왔다는 신호입니다.

   | 요구사항               | 패키지              | 버전    |
   | ---------------------- | ------------------- | ------- |
   | 지도 렌더링            | `expo-maps`         | 57.0.1  |
   | 위치 권한·추적         | `expo-location`     | 57.0.9  |
   | 백그라운드 위치        | `expo-task-manager` | 57.0.9  |
   | 실기기 네이티브 디버깅 | `expo-dev-client`   | 57.0.11 |

4. **앱 자체에 쓸 시간이 늘어납니다.** bare로 가면 New Architecture 대응, 빌드 설정, 서명, 배포 파이프라인을 직접 관리해야 합니다. 이 프로젝트의 목표는 빌드 인프라 시연이 아니라 **완성된 앱**이므로, 그 시간은 Phase 5(성능·배터리·권한 UX)에 쓰는 편이 낫습니다.

5. **EAS Build/Update로 배포까지 도달할 확률이 높아집니다.** 포트폴리오에서 "설치 가능한 빌드"의 유무는 큰 차이를 만들고, 이 레포가 실패했던 지점이 정확히 "완주하지 못함"입니다.

## 감수하는 것

- **config plugin이 없는 네이티브 SDK를 붙일 때 직접 plugin을 작성해야 합니다.** 다만 이는 네이티브 빌드 파이프라인 이해를 보여주는 가점 요인이기도 하므로, 발생하면 ADR로 기록합니다.
- **Expo Go로 실행할 수 없습니다.** 네이티브 모듈이 포함되므로 개발 빌드가 필수이고, 초기 진입에 빌드 1회가 추가로 필요합니다.
- 기존 `Dockerfile` APK 빌드 자산을 폐기합니다.
- EAS Build는 무료 티어에 빌드 횟수 제한이 있어 빌드 낭비를 관리해야 합니다.

## 되돌리는 비용

**낮음.** `npx expo prebuild`로 언제든 네이티브 폴더를 생성해 bare 워크플로로 전환할 수 있습니다. 되돌리기 싼 결정이므로 길게 고민하지 않고 확정합니다.
