# ADR-0004. 지도·위치 스택 선정

- 상태: **미결 — Phase 5에서 측정 후 확정**
- 일자: 2026-08-11 (작성) / 2026-08-12 (앱 컨셉 확정에 따라 M1 재정의) / 확정일: TBD

> 이 문서는 결정이 아직 내려지지 않은 상태로 열려 있습니다.
> **추정으로 채우지 않습니다.** 아래 측정 항목을 실기기에서 재고 그 숫자로 확정합니다.

## 맥락

앱 컨셉은 **경로 기록(산책/러닝)** 입니다. 걸은 경로를 지도에 기록하고 돌아보는 앱이며, 서버 없이 로컬만으로 완성 가능합니다.

이 컨셉의 핵심 난이도는 UI 구성이 아니라 다음 세 가지에 있습니다.

1. **긴 경로의 렌더링 성능** — 1시간 기록 = GPS 좌표 수천 개. 이걸 그대로 폴리라인으로 그리면 팬/줌이 무너집니다
2. **백그라운드 위치 추적과 배터리 소모의 트레이드오프** — 이 앱에서는 선택 기능이 아니라 **없으면 제품이 성립하지 않습니다**
3. **권한 거부 이후의 복구 경로** — iOS는 두 번째 권한 요청이 불가능

이 세 가지는 라이브러리 문서를 읽어서 답이 나오지 않고, **실기기에서 측정해야** 결정됩니다. 코드 생성이 저렴해진 환경에서 이 프로젝트의 실질적 변별점이 여기에 있습니다.

> **M1 재정의 이력**: 초안에서는 M1을 "마커 클러스터링 성능"으로 잡았습니다. 경로 기록 앱은 마커가 적어 클러스터링의 명분이 약한 반면, **폴리라인 좌표 수가 자연스럽게 수천 개로 늘어납니다.** 측정 대상을 마커 클러스터링에서 **폴리라인 데시메이션**으로 교체했습니다.

## 결정해야 할 것

### D1. 지도 라이브러리

| 후보 | 버전 | 장점 | 우려 |
|---|---|---|---|
| `expo-maps` | 57.0.1 | Expo 1st-party, SDK와 버전 동기화, 업그레이드 안정성 | 생태계가 젊음. 폴리라인 API 표현력을 먼저 확인해야 함 |
| `react-native-maps` | 1.29.0 | 성숙한 생태계, 폴리라인 관련 사례가 많음 | Expo SDK 업그레이드 시 별도 호환성 확인 필요 |

### D2. 폴리라인 데시메이션 방식

1시간 러닝 = 1초 간격이면 좌표 3,600개. 이걸 줄이는 방법.

- (a) **기록 시점 다운샘플링** — `distanceInterval`로 애초에 적게 받음. 단순하지만 경로 정확도 손실이 영구적
- (b) **저장 후 단순화** — Douglas-Peucker 등으로 원본은 보존하고 표시용만 축약
- (c) **줌 레벨별 적응형** — 줌 아웃 시 과감히 축약, 확대 시 원본에 근접

> (b)와 (c)는 조합 가능합니다. 원본 보존 여부가 "나중에 통계를 다시 뽑을 수 있는가"를 가르므로, 단순 성능 문제가 아닙니다.

### D3. 백그라운드 추적 정책

`expo-location`의 `Accuracy` 레벨 × 추적 간격 × `distanceInterval` 조합.

## 측정 계획

> 측정 없이 이 표를 채우면 오히려 감점입니다. 빈 칸으로 두는 편이 낫습니다.

### M1. 폴리라인 렌더링 성능

- 테스트 기기: (기종 / OS 버전 기입)
- 좌표 수: 500 / 1,500 / 3,600 (1시간) / 10,000 (마라톤)
- 측정 지표: 팬·줌 중 평균 FPS, 프레임 드랍 비율, 초기 렌더 시간

| 좌표 수 | 원본 그대로 FPS | 데시메이션 후 FPS | 시각적 손실 | 판정 |
|---|---|---|---|---|
| 500 | | | | |
| 1,500 | | | | |
| 3,600 | | | | |
| 10,000 | | | | |

**판단 기준:** 원본 그대로 3,600개에서 평균 55fps 이상이면 데시메이션은 불필요 — 넣지 않습니다. 미달 시 (b)를 먼저 적용하고, 10,000개에서도 미달이면 (c)까지 갑니다.

> **과잉 최적화를 경계합니다.** 측정에서 필요 없다고 나오면 넣지 않는 것도 기록할 가치가 있는 판단입니다.

### M2. 배터리 소모

- 측정 조건: 1시간 백그라운드 추적, 화면 꺼짐 상태
- 비교군: `Accuracy.Balanced` vs `Accuracy.High` × `distanceInterval` 10m / 50m

| 설정 | 1시간 배터리 소모 | 경로 정확도 | 좌표 수 | 판정 |
|---|---|---|---|---|
| Balanced / 50m | | | | |
| Balanced / 10m | | | | |
| High / 10m | | | | |

**판단 기준:** 시간당 소모 5% 이하를 목표로 하되, 경로가 실제 이동과 눈에 띄게 어긋나지 않는 선에서 결정. **이 표의 결과가 D2의 (a) 채택 여부를 함께 결정합니다.**

### M3. 권한 플로우

측정이 아니라 **경로 설계**입니다. 아래 상태 전부에 대해 화면이 정의되어야 합니다.

- [ ] 최초 요청 전
- [ ] 포그라운드 허용 / 백그라운드 미허용 → **기록 중 앱을 벗어나면 경로가 끊깁니다.** 이 앱에서 가장 치명적인 상태
- [ ] 전체 거부 → 설정 앱 유도 경로 (iOS는 재요청 불가)
- [ ] iOS 정밀 위치 끔(approximate location) → 경로 기록이 무의미해지는 수준
- [ ] 시스템 위치 서비스 자체가 꺼짐
- [ ] 기록 중 권한이 회수됨 (사용자가 설정에서 변경)

> 마지막 세 가지를 처리한 앱이 드뭅니다. **여기가 실질적 차별 지점입니다.**

## 되돌리는 비용

**D1은 높습니다.** 지도 라이브러리는 API 표면이 커서 후반에 교체하면 지도 관련 코드 대부분을 다시 씁니다. Phase 5 초반에 M1을 먼저 돌려 확정하고 들어가야 합니다.

**D2·D3은 낮습니다.** 데시메이션 방식과 추적 정책은 지도 컴포넌트 뒤에 격리 가능하므로, 인터페이스만 잘 분리해두면 나중에 바꿀 수 있습니다.
