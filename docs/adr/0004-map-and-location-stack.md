# ADR-0004. 지도·위치 스택 선정

- 상태: **미결 — Phase 5에서 측정 후 확정**
- 일자: 2026-08-11 (작성) / 확정일: TBD

> 이 문서는 결정이 아직 내려지지 않은 상태로 열려 있습니다.
> **추정으로 채우지 않습니다.** 아래 측정 항목을 실기기에서 재고 그 숫자로 확정합니다.

## 맥락

지도 기반 앱의 핵심 난이도는 UI 구성이 아니라 다음 세 가지에 있습니다.

1. **마커가 많을 때의 렌더링 성능** — 클러스터링을 JS에서 할지 네이티브로 넘길지
2. **백그라운드 위치 추적과 배터리 소모의 트레이드오프**
3. **권한 거부 이후의 복구 경로** — iOS는 두 번째 권한 요청이 불가능

이 세 가지는 라이브러리 문서를 읽어서 답이 나오지 않고, **실기기에서 측정해야** 결정됩니다. 코드 생성이 저렴해진 환경에서 이 프로젝트의 실질적 변별점이 여기에 있습니다.

## 결정해야 할 것

### D1. 지도 라이브러리

| 후보 | 버전 | 장점 | 우려 |
|---|---|---|---|
| `expo-maps` | 57.0.1 | Expo 1st-party, SDK와 버전 동기화, 업그레이드 안정성 | 생태계가 젊어 서드파티 클러스터링 래퍼가 없음 |
| `react-native-maps` | 1.29.0 | 성숙한 생태계, `react-native-map-clustering`(4.0.0) 등 기존 래퍼 활용 가능 | Expo SDK 업그레이드 시 별도 호환성 확인 필요 |

**이 선택이 D2를 제약합니다.** `expo-maps`를 고르면 클러스터링을 `supercluster`(9.0.0) 위에 직접 구현해야 합니다.

### D2. 클러스터링 방식

- (a) JS 클러스터링 — `supercluster` 9.0.0
- (b) 네이티브 클러스터링 위임
- (c) 뷰포트 기반 서버 사이드 클러스터링

### D3. 백그라운드 추적 정책

`expo-location`의 `Accuracy` 레벨 × 추적 간격 × `distanceInterval` 조합.

|---|---|---|---|

**판단 기준:** JS 클러스터링으로 2,000개에서 평균 55fps 이상이면 (a) 확정. 미달 시 (b) 또는 (c) 검토.

### M2. 배터리 소모

- 측정 조건: 1시간 백그라운드 추적, 화면 꺼짐 상태
- 비교군: `Accuracy.Balanced` vs `Accuracy.High` × `distanceInterval` 10m / 50m / 100m

| 설정 | 1시간 배터리 소모 | 위치 정확도 | 판정 |
|---|---|---|---|
| Balanced / 50m | | | |
| High / 10m | | | |

**판단 기준:** 시간당 소모 5% 이하를 목표로 하되, 정확도 손실이 기능을 해치지 않는 선에서 결정.

### M3. 권한 플로우

측정이 아니라 **경로 설계**입니다. 아래 상태 전부에 대해 화면이 정의되어야 합니다.

- [ ] 최초 요청 전
- [ ] 포그라운드 허용 / 백그라운드 미허용
- [ ] 전체 거부 → **설정 앱 유도 경로** (iOS는 재요청 불가)
- [ ] iOS 정밀 위치 끔(approximate location)
- [ ] 시스템 위치 서비스 자체가 꺼짐

> 마지막 세 가지를 처리한 앱이 드뭅니다. **여기가 실질적 차별 지점입니다.**

## 되돌리는 비용

**D1은 높습니다.** 지도 라이브러리는 API 표면이 커서 후반에 교체하면 지도 관련 코드 대부분을 다시 씁니다. Phase 5 초반에 M1을 먼저 돌려 확정하고 들어가야 합니다.

**D2·D3은 낮습니다.** 클러스터링 방식과 추적 정책은 지도 컴포넌트 뒤에 격리 가능하므로, 인터페이스만 잘 분리해두면 나중에 바꿀 수 있습니다.
